## Коллекция `knowledge`

Именованные векторы: `dense` (1024, Cosine) и `sparse`. Индексы payload по
`source`, `space`, `acl_groups`, `source_id`, `updated_at`. Создаётся
`init-collection.ps1`.

**Одна коллекция на все источники** с фильтром по `source`, а не коллекция на
источник.

Payload сразу заложен под мультиисточники и ACL: `source`, `source_id`, `space`,
`acl_groups`, `title`, `url`, `updated_at`, `chunk_idx`, `text`. Сейчас
`acl_groups = ["all"]`; при подключении Confluence туда пойдут реальные группы —
переиндексировать не придётся.

**ID чанка — детерминированный UUID (MD5) из `source|путь|номер`**, чтобы
повторный запуск обновлял точки, а не плодил дубли. Это фундамент инкрементальной
синхронизации. Критерий здоровья индексатора: второй прогон не меняет
`points_count`.

Sparse-вектор пока не пишется — Ollama отдаёт только dense. Гибридный поиск
доделаем на этапе качества.

## index-files.ps1

Читает `.md`/`.txt`, режет по заголовкам (~1500 символов), эмбеддинги с
`:11434/api/embed`, батчами по 16 в Qdrant.

Грабли PowerShell 5.1, уже вылеченные (не откатывать):

- **`.ps1` только ASCII или UTF-8 с BOM.** Без BOM 5.1 читает файл как cp1251 и
  падает на кириллице. Поэтому комментарии в скрипте английские
- `@(Split-Text ...)` — без обёртки файл из одного чанка схлопнется в строку, и
  range-индексация порежет её посимвольно
- `return ,$resp.embeddings` — запятая держит внешний массив, иначе `[0]`
  разворачивается и проверка врёт «vector size: 1»
- `Resolve-Path` для `-SourceDir` — относительный путь ломает `Substring`

Каша вместо кириллицы в выводе PowerShell — артефакт консоли, в Qdrant текст
хранится корректно. Проверять так: читать ответ как байты и декодировать UTF-8
явно.

## MCP-сервер поиска (СДЕЛАНО, работает end-to-end)

`kb/` — свой сервер, не форк `qdrant/mcp-server-qdrant` (тот умеет только
FastEmbed-модели, в наше пространство с bge-m3 не попадает).

- `kb/config.py` — настройки, порог релевантности
- `kb/embedder.py` — эмбеддинги через `/v1/embeddings` (задел на vLLM)
- `kb/retriever.py` — поиск в Qdrant, фильтры, фасеты для внятных ошибок
- `kb/server.py` — MCP streamable-http :8010, инструмент `kb_search`
- `kb/smoke_client.py` — проверка 4 сценариев настоящим MCP-клиентом
- `kb/tool_call_test.py` — проверка, зовёт ли модель инструмент

Запуск: `.venv\Scripts\python.exe -m kb.server`. Только чтение: писать в базу
может индексатор, но не модель — иначе ассистент начнёт «запоминать»
собственные галлюцинации в корпоративную вики.

**Порог релевантности `MIN_SCORE=0.48`** — dense-поиск возвращает результат
ВСЕГДА, даже на «рецепт борща». Замерено на testdocs: релевантные 0.57-0.65,
посторонние 0.27-0.42. Перепроверить на реальных данных.

**Проверено 14.08.2026:** тест вызова инструмента — 7/7 (qwen3:8b зовёт
`kb_search` на 4 вопроса про внутреннюю кухню, не зовёт на 3 общих вопроса про
Python и столицу Франции). В Continue (режим **Agent**, иначе MCP не работает)
полный цикл прошёл: вопрос про откат payment-gateway → ответ точно по чанку.

Подключение в `~/.continue/config.yaml`:
```yaml
mcpServers:
  - name: knowledge-base
    type: streamable-http
    url: http://localhost:8010/mcp
```

Известный недочёт: модель не ссылается на документ-источник, хотя инструмент
отдаёт его в поле `source`. Чинить системным промптом до подключения Confluence.

**`stateless_http=True` обязателен** (`kb/server.py`). По умолчанию сервер
выдаёт session-id и требует его в каждом запросе; Continue его не сохраняет и
падает с `-32600 Session not found` — причём перезагрузка окна НЕ помогает, это
не «зависшая сессия», а несовместимость режима. Заодно `json_response=True`
(обычный JSON вместо SSE). Бонус: перезапуск сервера больше не ломает Continue.

Ответы Continue настраиваются блоком `rules:` в `~/.continue/config.yaml`
(простые строки, склеиваются в системный промпт). Проверено: требование
указывать источник, запрет эмодзи и запрет дополнять ответ общими знаниями
работают на qwen3:8b.

SDK `mcp` 2.0 переименовал API: `FastMCP` → `MCPServer` (из `mcp.server`),
клиент `streamablehttp_client` → `streamable_http_client`, поля ответов в
snake_case (`server_info`, `input_schema`). Примеры из интернета под 1.x не
подходят.

### Замер 14.08.2026 (855 точек)

| Подход | Попаданий | Время |
|---|---|---|
| Только векторы | 13/15 (87%) | 1.2 с |
| + реранкер (CPU) | 14/15 (93%) | 48 с |
| + расширение всегда | 15/15 (100%) | 3.6 с |
| **+ расширение по необходимости** | **15/15 (100%)** | **1.85 с** |

**Расширение запроса обошло реранкер и по качеству, и по скорости** — и это
закономерно: реранкер переставляет найденное, а расширение чинит сам поиск,
доставая фрагменты, которые иначе не попадали в кандидаты. «Случайно удалил
ветку» -> `reflog` не брал даже реранкер, а расширение взяло.

Отсечка постороннего при этом цела: «рецепт борща», «столица Франции» —
по-прежнему пусто.

**Решение: работаем без реранкера.** Он добирает один вопрос («отложить
незаконченную работу» → `stash`), но это в пределах шума на выборке из 15, а на
CPU стоит 48 секунд. GPU-вариант вернул бы скорость, но решено отложить до
следующей версии. Сервис остаётся в compose под профилем `quality`.

Неподдающийся вопрос: «случайно удалил ветку» → `reflog`. Ранжированием не
лечится вообще: нужного чанка нет среди кандидатов. Только расширение запроса.

## Расширение запроса (ВКЛЮЧЕНО, `kb/expander.py`)

Модель генерирует 2 переформулировки вопроса в терминах документации, поиск
идёт по всем трём вариантам, результаты сливаются по RRF. Выключается
`KB_EXPAND=0`.

**Зачем.** Разрыв в словаре: пользователь пишет «отложить работу», в
документации `git stash`. Нужный чанк не попадает даже в кандидаты — исправлять
порядок нечем, поэтому реранкер тут бессилен.

Что важно в реализации:

- **Исходный вопрос всегда остаётся в наборе.** Исследование 2026 года («Out of
  Style: RAG's Fragility to Linguistic Variation») показало, что переписывание
  запроса стабильно вредит, когда искажает смысл. Оригинал — страховка
- **RRF складывает ранги, а не скоры**: `1/(60 + позиция)`. Скоры разных
  запросов несравнимы
- **В `score` остаётся лучший косинус, а не вес RRF** — порог `MIN_SCORE`
  откалиброван под косинус, подмена сломала бы отсечку постороннего
- **`reasoning_effort: "none"`** обязателен: без него секунда превращается в минуту

### Видеопамять: единый контекст обязателен

**`OLLAMA_CONTEXT_LENGTH=8192`, а не 32768.** Ollama считает разные размеры
контекста РАЗНЫМИ экземплярами модели. Прогрев на 32K плюс запрос приложения на
8K = два экземпляра qwen3 (7.6 + 5.4 ГБ), в 12 ГБ они не помещаются, начинается
вытеснение — и запрос ждёт 18-77 секунд загрузки. Это и был источник
`MCP error -32001: Request timed out` в Continue.

При едином контексте: qwen3 5.7 ГБ + bge-m3 0.7 ГБ = 8.7 из 12.3 ГБ, обе
резидентны, поиск 0.5-2.5 с. Для RAG 8K хватает: 5 фрагментов ≈ 2-3 тысячи
токенов.

Плюс `OLLAMA_MAX_LOADED_MODELS=2` (иначе держит одну) и `KEEP_ALIVE=2h` (при
15m модели выгружались за обед, первый запрос после простоя ждал 77 секунд).

Диагностика: `docker exec ollama ollama ps` — если модель одна или контексты
разные, будет тормозить. `nvidia-smi` для общей картины.

**Три грабли расширения запроса, каждая стоила замера:**

1. **`OLLAMA_MAX_LOADED_MODELS=2` обязателен.** Без него qwen3 и bge-m3
   вытесняют друг друга: расширение дёргает qwen3, эмбеддинги дёргают bge-m3,
   и каждый поиск платит ~17 секунд за загрузку модели с диска. Именно это
   вызывало `MCP error -32001: Request timed out` в Continue. Обе модели
   помещаются: 7.6 + 0.7 ГБ из 10.8 доступных
2. **`temperature: 0` в переформулировке.** При 0.3 варианты менялись от
   запуска к запуску, и один и тот же вопрос то находился, то нет —
   невоспроизводимые замеры
3. **Кандидатов брать с запасом на КАЖДЫЙ вариант** (`CANDIDATES`, не `top_k`),
   обрезать после слияния. Иначе фрагмент, найденный одной переформулировкой,
   не доезжает до топа: RRF поднимает тех, кто попал во все списки, а верный
   ответ обычно как раз редкая находка

**Маршрутизация по уверенности** (`EXPAND_IF_BELOW=0.62`): сначала обычный
поиск, расширение включается только если топовый скор ниже порога. Половина
вопросов идёт быстрым путём, среднее время 1.85 с вместо 3.6 с при том же
качестве. Порог подобран на 15 вопросах — мало, перепроверить на реальных данных.

**Промпт требует доменного контекста.** Первая версия без него выдала «упал
прод» -> «сбой продажного процесса» (модель прочла «прод» как «продажи») и
канцелярит вместо терминов. Пришлось прямо перечислить область (разработка,
DevOps, ИБ), запретить расшифровывать сокращения по-своему и дать примеры замен
(«отложить работу» -> git stash). После этого модель переформулирует на
английском — для мультиязычного bge-m3 это нормально, замер подтвердил.

## Реранкер (поставлен, ВЫКЛЮЧЕН)

Сервис `reranker` :8081 — TEI (Text Embeddings Inference от HuggingFace) с
`BAAI/bge-reranker-v2-m3`, **CPU-образ** `cpu-1.9` (686 МБ против ~5 ГБ у
GPU-варианта: в GPU-образе лежит CUDA-рантайм). Веса 2.2 ГБ в `D:\tei-cache`.
Включается `KB_RERANK=1`, адрес в `KB_RERANKER_URL` — сервис можно унести на
отдельную машину.

**Почему выключен.** На testdocs (14 чанков) пользы нет: реранкер отбирает
лучших из 20 кандидатов, отобранных из тысяч, а тут кандидаты = вся база и все
про одно и то же. Замер по 4 вопросам: 1 выиграл, 1 проиграл — шум. Плюс на CPU
~600 мс на пару, то есть ~9 секунд на запрос против <1 с у чистых векторов.

**Что важно знать при возврате к нему:**
- Оценки сырые (`raw_scores`), НЕ 0-1. На коротких выжимках релевантное +5..+7,
  нерелевантное −10..−11. Но на реальных длинных чанках ВСЁ уходит в минус
  (релевантное −5.5..−9, мусор −10..−11) — порог по нулю отрезает всё. Ставить
  порог по замеру на своих данных, не по теории
- GPU-вариант: тег `89-1.9` (Ada = RTX 40xx, у других поколений свой тег) плюс
  секция `deploy` с nvidia. ~1.1 ГБ видеопамяти, ~50 мс вместо 9 секунд
- Альтернатива: llama.cpp с `bge-reranker-v2-m3-Q8_0-GGUF` (~600 МБ) и флагами
  `--reranking --pooling rank`. **В Ollama реранкер не засунуть** — эндпоинта
  `/rerank` нет, PR #7219 висит с 2024

**qwen3 как реранкер — тупик, проверено.** С `reasoning_effort: none` она не
оценивает вовсе (раздаёт всем одинаковые баллы), с `low` судит безупречно
(верный 10/10, неверный 0/10), но 17 секунд на фрагмент. Генеративная модель
вынуждена рассуждать словами; cross-encoder сразу выдаёт число. На 35B будет
только хуже. Побочная находка: `reasoning_effort: "none"` ускоряет qwen3 с 63 с
до 1 с — пригодится для любых служебных вызовов.

**Настоящее узкое место — не ранжирование, а разрыв в словаре.** Пользователь
пишет «упал прод», в документе «дежурная смена DevOps». Такой чанк не доезжает
до реранкера вообще. Лечится расширением запроса: qwen3 переформулирует вопрос
в терминах предметной области перед поиском (один быстрый вызов с
`reasoning_effort: none`). Это следующий шаг по качеству, он бьёт точнее.

## Коннектор Confluence (СДЕЛАН, ждёт запуска на проде)

`confluence/` — выгрузка страниц в markdown. Подробности и порядок запуска в
`confluence/README.md`, он написан для запуска **в закрытом контуре без меня**.

- `sync.py` — обход API с пагинацией, инкрементальность по версии страницы
  (`.sync_state.json`), режимы `--check` / `--dry-run` / `--dump-raw` / `--full`
- `storage_to_md.py` — конвертер storage-формата (XHTML) в markdown
- `mock_server.py` — заглушка Confluence Server со сложной разметкой, на ней
  всё и отлажено
- Только стандартная библиотека: в контуре может быть нельзя ставить пакеты

Дальше обычным путём:
`.\index-files.ps1 -SourceDir ".\confluence\pages" -Source "confluence"`.
Проверено end-to-end на заглушке: 3 страницы -> 5 чанков -> поиск находит
(вопрос про аппрувы дал 0.756).

**Грабли конвертера, найденные заглушкой** (все исправлены, не откатывать):

1. **HTML-сущности ломают XML-парсер.** `&mdash;`, `&nbsp;` не входят в пятёрку
   известных XML, парсер падает — и страница уходила в запасной путь, плоским
   текстом без заголовков и таблиц. Раскрываем заранее, кроме XML-безопасных
2. **Таблица и список — ОДИН элемент вывода.** Элементы склеиваются через
   пустую строку, а чанкер режет длинные разделы по ним: таблица развалилась
   бы на строки, список — на пункты, и «шаг 3» потерял бы «шаги 1-2»
3. **Ссылки и картинки прячут смысл в атрибутах.** `<ac:link>` внутри абзаца
   даёт пустоту при `itertext()` — выходило «Подробнее см. .». Подменяем их
   текстом до разбора

Не реализовано: вложения, комментарии, реальные ACL (пока `["all"]`),
Confluence Cloud (там другая аутентификация и путь `/wiki/rest/api/`).

## Коннектор Jira (НАПИСАН, на живой Jira не проверялся)

Только **Jira Server/Data Center**. Cloud не поддержан намеренно: там другая
аутентификация, путь `/rest/api/3` и описание в формате ADF (JSON-дерево
вместо вики-разметки) — это отдельный парсер.

Порядок запуска, проверки и разбор типовых проблем — в `jira/README.md`, он
написан для запуска **в закрытом контуре без меня**.

Три части:

- `jira/sync.py` — выгрузка задач в JSON, по файлу на задачу
  (`<PROJECT>/<KEY>.json`). Инкрементальность через `updated >= <дата>` и
  `.sync_state.json`, режимы `--check` / `--dry-run` / `--dump-raw` / `--full`
- `kb/jira_index.py` — раскладка задач в Qdrant с полями в payload
- `kb/jira_retriever.py` + инструмент `jira_search` в `kb/server.py`

**Почему не через markdown и `doc_index`, как Confluence.** Вопрос к задачам
почти всегда начинается с фильтра: «что на Иванове», «что открыто в DEVSEC».
Исполнитель и статус в ТЕКСТЕ задачи не написаны — они поля, и векторный поиск
о них не знает. Поэтому поля едут в payload с индексами, а вектор остаётся для
смысловой части. Отсюда три правила в `jira_retriever.py`:

1. Есть человек/проект/статус — сначала фильтр, поиск работает внутри отбора
2. Смысловой части в вопросе нет («какие задачи на Иванове») — вектор не
   считаем вовсе, отдаём свежие по `updated`. Это выборка, а не поиск
3. **`MIN_SCORE` применяется, только когда фильтров нет.** Внутри «задач
   Иванова» косинусы низкие просто потому, что выбирать не из чего, и порог,
   честный для всей базы, выкосил бы верные ответы

**Охват — единственная реальная граница.** Аутентификации на портах нет,
`acl_groups` заглушка, так что ограничивать доступ к индексу нечем; ограничиваем
его содержимое. Три рамки в `.env`: `JIRA_PROJECTS` (ключи проектов),
`JIRA_TEAM` / `JIRA_TEAM_GROUP` (состав команды, логины или группа Jira) и
`JIRA_SINCE` (глубина истории: `30d`, `6M`, дата; флаг `--since` перебивает).
Третья появилась из практики: 10 тысяч задач — это ~30 тысяч чанков, и почти
всё время первого прогона уходит на эмбеддинги, а не на запросы к Jira. Окно в
месяц режет объём на порядок, а старые задачи в поиске всё равно шумят.
Ловушка JQL: строчная `m` — это МИНУТЫ, месяцы — заглавная `M`; на строчную
скрипт предупреждает вслух.
Второе фильтрует по исполнителю, то есть **бэклог без исполнителя не приедет** —
если он нужен, условие пишется руками в `JIRA_JQL`. В payload сразу
`acl_groups = ["jira:<PROJECT>"]`, а не `["all"]`: когда авторизация появится,
переиндексировать не придётся.

Комментарии индексируются отдельными чанками, и это важно: ответ обычно лежит
не в описании, а в обсуждении. Перед эмбеддингом к каждому чанку приклеивается
`KEY: заголовок` — комментарий вроде «сделал, проверь» без этого не находится
вообще. Если обсуждение длиннее одной порции API, `sync.py` дочитывает его
отдельным запросом: у самых обсуждаемых задач иначе в индекс попадало бы только
начало разговора.

**`kb_search` не видит задачи.** Jira лежит в общей коллекции `knowledge`, и
пока поиск по документации искал по всему подряд, на вопрос про Jira модель
получала похожий по словам текст из Confluence — то есть уверенный неверный
ответ. Теперь `_build_filter` в `kb/retriever.py` подставляет `must_not` по
`OWN_TOOL_SOURCES = ("jira",)`, если источник не задан явно; `source_filter="jira"`
как лазейка остался. Правило общее: **у источника есть свой инструмент — значит
из общего поиска он исключается.**

**Поиск по номеру задачи — отдельный путь** (`get_issue`), не частный случай
смыслового поиска: номер вида `DEVSEC-412` эмбеддеру почти ничего не говорит, и
векторный поиск его не находит. Номер, ошибочно положенный моделью в `query`,
перехватывается регуляркой `ISSUE_KEY` и уходит туда же.

**`applied_filters` в ответе.** Разбор типовых отказов RAG сходится в том, что
больше всего промахов случается ДО поиска: фильтр молча выбрасывает нужное, и
«в базе нет» не отличить от «спросили не то». Поэтому инструмент возвращает,
что реально применилось, — с РАЗРЕШЁННЫМ именем человека, а не с тем, что
спросили: под «Иванов» мог подставиться однофамилец.

**Вызов только по слову «jira»** («@jira», «жира», «джира») — условие жёстче,
чем у `kb_search`/`code_search` с их глаголами-обращениями, и потому надёжнее:
слово редкое и случайно не появляется. В описании инструмента отдельно разобрана
главная ошибка модели — класть фамилию в `query` вместо `person`.

Проверено на синтетических данных (4 задачи, временная коллекция
`jira_selftest`): выборка по человеку и по логину, однофамильцы дают просьбу
уточнить, `открытые`/`закрытые` разбираются в категорию статуса, «не назначен»
работает, смысловой поиск внутри выборки находит ответ в комментарии (0.535).
**На живой Jira не запускалось** — первым делом `python jira/sync.py --check`.

Не реализовано: удалённые и перенесённые задачи остаются в выгрузке и в индексе;
вложения; история изменений; связи между задачами.

## DefectDojo (НАПИСАНО, на живом стенде не проверялось)

Четвёртый источник, механика как у остальных: выгрузка -> индекс -> поиск.
**Отдельный MCP-сервер на :8012**, а не инструмент рядом с поиском.

- `kb/dojo.py` — HTTP-клиент (`Authorization: Token <ключ>`, API v2 Key из
  профиля), проверка связи `python -m kb.dojo --check`
- `kb/dojo_index.py` — забирает находки по API и пишет в Qdrant.
  **Без промежуточных файлов**, в отличие от Confluence и Jira: у находки нет
  тяжёлого тела, перезабрать по API дешевле, чем поддерживать каталог. Если
  DefectDojo не виден с машины с Qdrant — есть `--dump` и `--from`
- `kb/dojo_retriever.py` — поиск по индексу
- `kb/dojo_server.py` — сервер :8012 с единственным инструментом
  `dojo_findings`. Образ общий с `kb`, отличается только командой запуска;
  индекс наполняет `kb` (`python -m kb.dojo_index`)

**Почему отдельный сервер.** Не ради выбора инструмента — на него это не
влияет вовсе: клиент показывает модели все инструменты одним плоским списком,
независимо от того, с какого они сервера. Ради ДОСТУПА: аутентификации внутри
нет, и порт — единственный рычаг. :8010 открывается всей команде, :8012 со
списком уязвимостей — только AppSec и сборочному агенту, правилом на
брандмауэре. Плюс это соответствует практике «один сервер — одна работа»
(ориентир 5-15 инструментов на сервер, деление по доменам и по ролям
пользователей). Пользователю, которому уязвимости не положены, достаточно
удалить блок `defectdojo` из своего конфига Continue.

**Живой запрос обсуждался и отложен** (решение пользователя, пилот): сначала
как все, реальное время потом. Клиент для этого уже написан — переключение
будет правкой в `dojo_findings`, не переделкой. Плюс индекса, которого у
живого режима нет: смысловой поиск по описаниям и рекомендациям.

Ключевые решения:

- **Сводка по уровням возвращается всегда**, даже когда спросили про один.
  «Три критичных» без общей картины вводит в заблуждение: непонятно, три из
  трёх это или три из сорока
- **Счётчики считают находки, а не чанки.** У находки их несколько, поэтому в
  фильтр счётчика добавлено `chunk_idx = 0` — иначе «критичных: 40» означало
  бы 12 находок
- **Переиндексация сносит все точки продукта целиком**, а не только
  обновлённые: закрытая находка исчезает из выдачи API, и без этого ассистент
  продолжал бы показывать её как открытую
- Продукт ищется по неполному имени («abinf» -> «ABInf Backend»), несколько
  кандидатов -> просьба уточнить. Список продуктов фильтруется НА НАШЕЙ
  стороне: у разных версий DefectDojo фильтр по имени ведёт себя по-разному
- Имя сканера и статус собираются защитно (`scanner_name`, `finding_status` в
  `dojo.py`): ключи различаются между сборками, четыре флага статуса
  сворачиваются в одно слово
- Только чтение. Галлюцинация, закрывшая уязвимость, — это инцидент

**`DOJO_PRODUCTS` — граница доступа, а не удобство.** Пока на :8010 нет
аутентификации, список уязвимостей может запросить любой, кто дотянулся до
порта. Для пилота это принято осознанно; до раскатки на людей порт закрыть.

Вызов по слову «dojo»/«defectdojo». Проверено на синтетике (5 находок):
фильтры по состоянию и уровню, сводка, смысловой поиск, `kb_search` находки не
видит.

## Граф кода (СДЕЛАНО, `code/`)

Отдельный MCP-сервер на :8011 — Graphify поверх склонированных репозиториев.
Подробности в `code/README.md`.

**Почему Graphify, а не свой разбор через `ast`:** открытый проект на
tree-sitter, даёт типизированные связи (calls/imports/contains), обратный обход
(что сломается), поиск хабов и **встроенный MCP-сервер**. Своё писать — неделя
работы ради худшего результата.

**Ключевое для закрытого контура:** `graphify update <path>` работает
**полностью офлайн**, без ключей и сети (tree-sitter локально). LLM нужен
только для семантических меток по документам — нам не требуется. В образе
обязательно `graphifyy[mcp]`, иначе HTTP-транспорт не поднимется.

Проверено: SecretVuln — 473 узла за 7 секунд, `affected "require_permission"`
верно нашёл все роутеры, которые его импортируют. На `psf/requests` (1179
узлов) `god_nodes` выдал реальное ядро библиотеки: Response, PreparedRequest,
Session.

Continue подключён к ДВУМ серверам сразу: `knowledge-base` :8010 (вики) и
`code-graph` :8011 (код). Это штатно.

Обновление: `docker compose exec code-graph /app/sync.sh` (git fetch +
пересборка графа + слияние репозиториев), можно на планировщик.

## Смысловой поиск по коду (СДЕЛАНО)

`kb/code_index.py` — индексатор, `kb/code_retriever.py` — поиск, инструмент
`code_search` в том же MCP-сервере :8010 (рядом с `kb_search`).

Отвечает на «где у нас реализовано X», «куда править, чтобы добавить Y».
Возвращает `location` вида `репозиторий/файл.py:42` — конкретное место.
Дополняет граф: граф знает связи, но не знает смысла.

Индексация: `python -m kb.code_index D:\code-data\repos [--recreate]`.

Решения:

- **Чанк = функция или класс целиком** (разбор через `ast`, стандартная
  библиотека). Разрезанная пополам функция бесполезна: по ней нельзя ни
  понять логику, ни показать человеку, куда идти
- **Перед эмбеддингом шапка** — репозиторий, путь, символ, сигнатура,
  докстринг. Метод `_check` в вакууме неотличим от сотни других `_check`
- **Отдельная коллекция `code`**, не общая: кода в разы больше документации,
  он утопил бы вики в выдаче. Свой порог (0.35 против 0.48 — код
  формулируется иначе, чем задача)
- **Тесты, миграции, вендор исключены.** Каталоги `tests/` целиком: фильтр по
  имени файла их не ловит (`tests/__init__.py`), а в выдаче они вытесняют саму
  реализацию — проверено, лезли первыми
- **`os.walk`, а не `rglob`**: в репозиториях бывают симлинки на несуществующие
  цели, Windows даёт `WinError 1920`, и `rglob` обрывает обход целиком

Проверено на `psf/requests` (328 чанков): «где обрабатываются куки» ->
`PreparedRequest.prepare_cookies`, «проверка ssl сертификатов» ->
`HTTPAdapter.cert_verify`, «как формируется заголовок авторизации» -> все три
места в `auth.py`.

**Сценарий, ради которого делалось:** «нужно добавить X» -> `code_search`
находит место -> инструменты графа показывают, кто это вызывает и что
сломается.

### Обновление кода — одной командой

```powershell
.\update-code.ps1
```

Делает всё: git pull в контейнере `code-graph`, пересборка графа, затем
переиндексация векторов в контейнере `kb`. Вешается на планировщик
(`schtasks`, пример в шапке скрипта).

Обе части намеренно в одной команде: если обновлять только граф, поиск начнёт
отдавать устаревшие строки файлов, и заметят это не сразу.

Для этого `kb` монтирует `D:\code-data` только на чтение — репозитории
клонирует `code-graph`, а индексирует их `kb`.

**Грабли:**
- **`CODE_REPOS` держать в `.env`**, а не в переменной сеанса: после
  перезапуска список терялся, и синхронизация молча ничего не делала
- **В `.ps1` не ставить `$ErrorActionPreference = "Stop"`**: docker и python
  пишут информационные сообщения в stderr, и PowerShell обрывает скрипт на
  ровном месте. Успех проверять по `$LASTEXITCODE`
- **`.ps1` сохранять в UTF-8 с BOM** — записано в конвенциях, но я снова
  наступил: без BOM PowerShell 5.1 читает файл как cp1251 и падает на
  кириллице с «string is missing the terminator»

### Грабли: модель выдумывает АРГУМЕНТЫ, а не ответ

У инструментов Graphify есть необязательный `project_path`. qwen3:8b заполняла
его наугад (`/workspace`), инструмент отвечал `graph.json not found: ...`, а
модель пересказывала это как «граф не сгенерирован» — и один раз сочинила
несуществующие скрипты и ссылку на `internal.example.com`.

Выглядело как «модель игнорирует инструмент», на деле — сломанный вызов.
Лечится правилом в Continue: не заполнять `project_path`, звать без аргументов
или только с `top_n`.

**Вывод на будущее:** когда инструмент ведёт себя странно, смотреть надо не
только на ответ, но и на аргументы вызова, и на схему инструмента
(`list_tools`). Необязательные параметры с описанием «путь к чему-то» —
приглашение для модели что-нибудь выдумать; такие лучше закрывать правилом.

`Error loading resource templates ... -32601: Method not found` в интерфейсе
Continue — **безобидно**: Continue спрашивает список ресурсов, Graphify их не
реализует. Инструменты работают.

## Развёртывание на сервере (ГОТОВО)

`DEPLOY.md` — инструкция целиком, рассчитана на самостоятельный запуск в
закрытом контуре.

- `deploy.sh` — с нуля: контейнеры, модели, коллекции, индексация, проверка.
  Останавливается на первой ошибке и объясняет, что делать
- `healthcheck.sh` — контейнеры, сервисы, модели, наполненность коллекций и
  **живой поиск** (не «порт открыт», а «запрос что-то находит»). Код возврата
  0/1, годится для мониторинга
- `update-code.sh` — репозитории, граф и векторный индекс одной командой,
  вешается на cron
- `continue-rules.yaml` — правила для Continue, скопировать в конфиг
- `.env.example` — все настройки с объяснениями

**Всё развязано по путям**: compose читает `MODELS_DIR`, `QDRANT_DIR`,
`CODE_DIR`, `DOCS_DIR` и порты из `.env`. На Windows пути вида `D:\...`, на
Linux `/srv/local-ai/...` — стек один и тот же.

**`kb/doc_index.py`** — индексатор документов на Python вместо
`index-files.ps1`: тот работал только под Windows, а на сервере нужен запуск в
контейнере. Логика та же (заголовки в крошки, не резать блоки кода,
детерминированные id, удаление старых точек файла). PowerShell-версия осталась
для локальной работы.

Грабли развёртывания:

- **Окончания строк в `.sh` только LF.** С CRLF bash на Linux не запустит
  скрипт вовсе
- **Раскладывать документы по подкаталогам и индексировать с разными
  `--source`.** Свалил всё в один каталог — книга проиндексировалась второй раз
  как `local`, в коллекции стало 1689 точек вместо 843
- **Git Bash подменяет пути** в `docker compose exec`: `/docs/internal`
  превращается в `C:/Program Files/Git/docs/internal`. Запускать из PowerShell
  либо ставить `MSYS_NO_PATHCONV=1`

После порта индексатора замер дал 14/15 против 15/15 у PowerShell-версии, и
чанков 829 против 841 — разбиение слегка расходится. В пределах шума этого
набора (мы уже видели, как проваленный вопрос перескакивает), но разница
реальная: при расширении набора вопросов проверить.

## Запуск после перерыва

```powershell
cd ~\Desktop\LOCAL-AI
docker compose up -d
```

Поднимает всё: `ollama` :11434, `qdrant` :6333, `kb` :8010 (MCP-сервер в
контейнере, собирается из `Dockerfile`). Реранкер не поднимается — он под
профилем `quality`.

После правки кода в `kb/`: `docker compose up -d --build kb`.

Локальный venv остался для отладки и `index-files.ps1` — но сервер теперь
живёт в контейнере, руками его запускать не нужно.

**Проверять `kb` через `curl http://localhost:8010/mcp` НЕЛЬЗЯ** — GET по этому
адресу открывает поток и висит до таймаута. Проверка: `python -m
kb.smoke_client` (нужен venv) или просто логи контейнера.

Внутри контейнера соседи доступны по именам (`http://ollama:11434`,
`http://qdrant:6333`), а не по localhost — он там указывает на сам контейнер.

Если контейнер `Up`, но `curl` даёт `http=000` — Docker Desktop потерял проброс
портов после перезапуска WSL. Лечится `docker restart <имя>`, данные не
задеваются (они на `D:`).

Прод-модель планируется `qwen3-coder:30b` — на 12 ГБ не влезет, нужно железо от
48 ГБ. Позже переезд с Ollama на vLLM, **поэтому все новые вызовы — через
OpenAI-совместимый `/v1`**, не через `/api/*`. Текущий `index-files.ps1` ещё на
`/api/embed`: менять протокол одновременно с чем-то ещё не стоит, это отдельный шаг.
