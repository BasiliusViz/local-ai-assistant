# Проба OASIS: команды

Цель пробы — не внедрить инструмент, а понять, стоит ли: сколько времени
занимает прогон и какая доля находок осмысленная.

Цепочка: `OASIS (контейнер) → прокси (ваша машина) → шлюз → Ollama`.
Прокси нужен потому, что OASIS умеет указать адрес модели, но не умеет
передать ключ, а шлюз без `x-api-key` отвечает 403.

---

## Окно 1: прокси

Оставить работать до конца пробы.

```powershell
cd $HOME\Desktop\LOCAL-AI
```

```powershell
.\.venv\Scripts\python.exe ollama_proxy.py --bind 0.0.0.0
```

## Окно 2: всё остальное

Проверить, что прокси отвечает и ключ подставляется:

```powershell
curl http://localhost:11435/api/tags
```

Скачать OASIS:

```powershell
git clone https://github.com/psyray/oasis.git $HOME\Desktop\oasis
```

```powershell
cd $HOME\Desktop\oasis
```

Собрать образ:

```powershell
docker compose build
```

Проверить, что контейнер достучится до модели через прокси:

```powershell
docker compose run --rm oasis --list-models -ol http://host.docker.internal:11435
```

Прогон по одному каталогу:

```powershell
docker compose run --rm -v D:\code-data:/code:ro oasis -i /code/ВАШ-ПРОЕКТ/app -sm qwen3.6:35b -m qwen3.6:35b -em bge-m3 -ol http://host.docker.internal:11435 -v
```

---

## Что подставить своё

- `D:\code-data` — ваш каталог с кодом (`CODE_DIR` из `.env`)
- `ВАШ-ПРОЕКТ/app` — путь к каталогу внутри него, начиная с `/code`
- `qwen3.6:35b` — имя модели из вывода `--list-models`

## Почему команды именно такие

`--bind 0.0.0.0` у прокси — чтобы он принимал подключения от контейнера.
Наружу это не уйдёт: входящие закрыты брандмауэром Windows.

`host.docker.internal` — так контейнер обращается к вашей машине. Внутри
контейнера `localhost` означает его самого, поэтому адрес прокси нельзя
написать как `localhost`.

`-v D:\code-data:/code:ro` — ваш код виден контейнеру как `/code`, только на
чтение. Поэтому путь в `-i` начинается с `/code`, а не с `D:\`.

Почему именно `/code`, а не `/work`: в их `docker-compose.yml` каталог самого
OASIS уже смонтирован как `/work`, и туда же он кладёт отчёты. Подключив свой
код в `/work`, вы затёрли бы это монтирование и потеряли результаты — они
остались бы внутри контейнера и исчезли с ним.

Отчёты поэтому появятся прямо в `$HOME\Desktop\oasis` на вашей машине,
отдельный том под них не нужен.

Прогон идёт **по одному каталогу, не по репозиторию**: OASIS рассчитан на две
модели — лёгкая просеивает весь код, тяжёлая разбирает подозрительное. У нас
одна на обе роли, поэтому просеивание идёт тяжёлой и это медленно.

## Что смотреть по итогу

**Время на каталог.** Умножьте на размер репозитория — станет понятно, реально
ли это по расписанию или нужна лёгкая модель на первую ступень.

**Доля осмысленных находок.** Главный вопрос. Если из десяти находок восемь
мусор, инструмент создаёт работу вместо экономии, и дальше идти незачем.

**Отчёты** — в каталоге OASIS на вашей машине, в нескольких форматах: HTML
посмотреть глазами, SARIF для импорта в DefectDojo, если решим продолжать.

## Если проба удалась

1. Контейнер рядом со стеком, код примонтирован только на чтение
2. SARIF уезжает в DefectDojo — **в отдельный продукт и не в статусе
   «открыта»**: смешивать находки LLM с находками Semgrep в одних метриках
   значит испортить метрики
3. Расписание раз в неделю по изменившимся репозиториям
4. Просить лёгкую модель для первой ступени

## Ограничения

- Лицензия GPL v3 — для внутреннего использования нормально, юристам показать
- Форк сторонний, код перед вводом в контур стоит прочитать: инструмент
  получает доступ ко всему исходному коду и ходит в модель
- Три модели по очереди на одной видеокарте упираются в перезагрузку. Пока
  обходим одной
- Только чтение репозиториев. Никаких правок кода и никакой записи в
  DefectDojo сверх импорта находок
