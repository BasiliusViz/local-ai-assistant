## Зачем

README в репозиториях релиза почти пустые («ничего путного нет» — пользователь), карточки
из них бедные. Пользователь не знает продукт и хочет, чтобы модель прочитала код и сама
написала README, а потом по нему отвечала (`cb_repos`, Obsidian).

Что модель видит, чтобы понять назначение (любой язык, не только Jenkins):
- **скелет большого файла** — сигнатуры **плюс докстринги и первые строки комментариев**
  (функции и файла; строки берутся с диска по `loc` узла);
- **точки входа, зависимости, конфиги** (`__main__`, `main.go`, `Dockerfile`, cron,
  `requirements.txt`/`go.mod`/`pom.xml`, `.env`/`.yaml` — порты, адреса, топики) — всегда
  целиком в вызов README, независимо от порога;
- **подсказки пользователя** — `CODE_DIR/.summaries/hints.txt`, строка `репо: что это`;
  модель берёт как факт, остальное — по коду. Для непонятных репозиториев, не для всех;
- в промпте: не выдумывать; назначение, угаданное только по именам, — «предположительно».
  В README пометка «сгенерировано моделью».

Ответ модели на папку — JSON `{"summary": "3–5 фраз", "tags": [...]}`: теги — в том же
вызове, бесплатно; файл наследует теги папки. Словарь тегов — позже, слой тегов
(отдельный план). Теги на каждый файл отдельным вызовом отклонены: файлов в разы больше
папок, сутки вместо ночи, а понимания тег не даёт.

Последний шаг — **обзор системы** одним вызовом (или по группам): все README + связи между
репозиториями (граф, `jenkins_graph`, адреса/топики из конфигов) -> «как всё связано»,
`.summaries/_system.md`.

Проверка — вопросами (пользователь): 10–20 вопросов по знакомым репозиториям
(«что делает X», «где деплой в прод», «кто ходит в billing») с ожидаемым ответом; прогон
в Continue до и после README, счёт — ответил верно / частично / нет.

## Решение: пересказ снизу вверх по папкам

Весь код в контекст не влезет (`main` — 2 млн узлов графа). Модель каждый раз видит одну папку:

```
скелет файлов (без модели) -> пересказ папки (модель) -> ... -> README репозитория (модель)
```

1. **Файл — без модели:** маленький (до ~8 КБ — Jenkins-скрипты, `.sh`, конфиги) — целиком:
   по сигнатурам его не понять. Большой — скелет: функции/классы/методы с сигнатурами и
   строкой из графа (узлы с `source_file`, `loc`), как «карта репозитория» у aider. Файлы
   берутся с диска, так что и те, которых нет в графе (Graphify их не разбирает), учтены.
2. **Папка — один вызов:** её файлы/скелеты + пересказы подпапок -> 3–5 фраз. Мелкие папки
   (порог — объём входа, ~1–4 тыс. токенов) сливаются в родительскую целиком: их текст
   читается в вызове родителя, а не теряется. Пересказ хранится с хешем входа:
   повторный прогон считает только изменившееся.
   **Jenkins** (`code/jenkins_graph.py`): пайплайн — это вызовы шагов общей библиотеки
   (`abActions(...)` = `vars/abActions.groovy`, часто в другом репозитории). Поэтому сначала
   пересказываются репозитории-библиотеки (по строке на шаг), а к пересказу пайплайна
   подмешиваются описания шагов, которые он зовёт (связи из `jenkins_graph.build`).
3. **Репозиторий — один вызов:** пересказы верхних папок + манифесты, зависимости, точки входа
   (`main.go`, `*Application.java`, Dockerfile), конфиги (порты, адреса, топики) -> README:
   назначение, части, вход/выход, зависимости.
4. **В карточку:** поле «описание (сгенерировано моделью)» рядом с настоящим README, с
   пометкой. В `cb_repos`, Obsidian (по желанию — заметка на модуль), `services.yaml` (purpose).

Вызовы модели — через `/v1`, `reasoning_effort: "none"`, только stdlib.
