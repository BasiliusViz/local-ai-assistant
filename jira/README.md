# Задачи Jira в базе знаний

Выгрузка задач из Jira Server/Data Center, индексация в Qdrant и поиск по ним
инструментом `jira_search`. Всё запускается в контейнере `kb` — Python на
сервере не нужен.

**Только Server/DC.** У Jira Cloud другая аутентификация, путь `/rest/api/3` и
описание в формате ADF — это отдельный парсер, здесь его нет.

## Настройки

В корневом `.env`, там же, где остальной стек. Обязательны три:

```
JIRA_URL=https://jira.company.local
JIRA_TOKEN=personal-access-token
JIRA_PROJECTS=DEVSEC,PLAT
```

Остальное сужает выборку и не обязательно:

| Переменная | Что делает |
|---|---|
| `JIRA_TEAM` | логины команды через запятую — только их задачи |
| `JIRA_TEAM_GROUP` | то же, но составом рулит Jira |
| `JIRA_SINCE` | глубина истории: `30d`, `6M` или дата `2026-08-01` |
| `JIRA_JQL` | своё условие, складывается через AND |
| `JIRA_COMMENTS` | `1` (по умолчанию) — тянуть комментарии, `0` — нет |
| `JIRA_USER` / `JIRA_PASSWORD` | вместо токена, для Jira старше 8.14 |

Три вещи, на которых спотыкаются чаще всего:

1. **`JIRA_TEAM` — это логины, а не фамилии.** Логин виден в адресе профиля:
   `.../secure/ViewProfile.jspa?name=i.ivanov`
2. **Строчная `m` в JQL — это МИНУТЫ.** Месяц — `1M`, месяц днями — `30d`
3. **Правка `.env` не действует на работающий контейнер.** Переменные
   подставляются при создании: после правки `docker compose up -d kb`

## Порядок запуска

```bash
docker compose up -d --build kb
```

```bash
docker compose exec kb python jira/sync.py --check
```

`--check` печатает, под кем подключились, и по каждому проекту две цифры:
сколько задач всего и сколько поедет с учётом команды и окна. **Совпали —
условия не сработали**, дальше идти бессмысленно.

```bash
docker compose exec kb python jira/sync.py --dry-run
```

```bash
docker compose exec kb python jira/sync.py
```

```bash
docker compose exec kb python -m kb.jira_index /docs/jira
```

Перезапускать `kb` после индексации не нужно: сервер читает Qdrant на каждый
запрос. Повторные прогоны инкрементальны — едут только изменившиеся задачи.

Пока идёт индексация, **не дёргайте ассистента в Continue**: расширение запроса
зовёт qwen3 и вышибает эмбеддер из видеопамяти, каждый такой раз стоит десятки
секунд.

## Проверки, когда что-то не работает

Идут от данных к модели: на каждом шаге видно, дальше искать причину или уже
нашли.

### 1. Что лежит в индексе

```bash
docker compose exec kb python -c "
from kb import jira_retriever as jr
print('есть задачи:', jr.available())
print('проекты:   ', jr.values('project'))
print('статусы:   ', jr.values('status'))
print('исполнители:', jr.values('assignee')[:30])
"
```

Главная проверка. Чаще всего поиск «не находит человека» потому, что в Jira он
записан не так, как его спрашивают: «Иванов И.И.» вместо «Иванов», латиница
вместо кириллицы. Сопоставление идёт по вхождению и по началу слов, но через
смену алфавита не перепрыгнет.

### 2. Сколько всего чанков задач

```bash
curl -s -X POST 'http://localhost:6333/collections/knowledge/points/count' -H 'Content-Type: application/json' -d '{"filter":{"must":[{"key":"source","match":{"value":"jira"}}]},"exact":true}'
```

Ориентир: примерно 2–4 чанка на задачу (карточка с описанием плюс комментарии).
Если цифра сильно больше ожидаемой — в индексе остались задачи от прошлых
прогонов, см. «Полная пересборка».

### 3. Поиск напрямую, без модели

Выборка по человеку:

```bash
docker compose exec kb python -c "
from kb import jira_retriever as jr
for i in jr.search_issues(person='Иванов', top_k=5):
    print(i.key, '|', i.status, '|', i.assignee, '|', i.summary[:50])
"
```

Смысловой поиск:

```bash
docker compose exec kb python -c "
from kb import jira_retriever as jr
for i in jr.search_issues(query='дедупликация', top_k=5):
    print(round(i.score,3), i.key, '|', i.found_in, '|', i.summary[:50])
"
```

`found_in` показывает, где нашлось — в описании или в комментарии.

### 4. Сам MCP-инструмент, как его зовёт Continue

```bash
curl -s -X POST http://localhost:8010/mcp -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"jira_search","arguments":{"person":"Иванов","top_k":5}}}'
```

Данные приходят здесь, но не в чате — значит Jira-часть исправна, а модель
зовёт инструмент не с теми аргументами.

### 5. Сервер вообще отдаёт три инструмента?

```bash
curl -s -X POST http://localhost:8010/mcp -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Должны быть `kb_search`, `code_search` и `jira_search`. Третьего нет — образ
собран из старого кода, вернитесь к `docker compose up -d --build kb`.

## Что отдаёт `jira_search`

Аргументы: `query`, `person`, `role` (`assignee` или `reporter`), `project`,
`status`, `issue_key`, `top_k`, `response_format`.

Кратко: `key`, `summary`, `status`, `assignee`, `updated`, `url`. Поле `text`
добавляется, только когда задача найдена смысловым поиском или запрошена по
номеру, — в простой выборке это была бы карточка, уже разобранная по полям.

Вместе с результатом возвращается `applied_filters` — что реально применилось.
Смотрите туда первым делом, когда «нашлось не то»: под «Иванов» мог
подставиться однофамилец, а «открытые» — превратиться в набор колонок
конкретного проекта.

`issue_key` — точный поиск по номеру (`DEVSEC-412`), отдельным путём в обход
вектора: номер задачи эмбеддеру почти ничего не говорит, и смысловым поиском не
находится. Номер, положенный в `query` по ошибке, перехватывается и уходит туда
же.

Подробно (`response_format: "detailed"`): плюс `type`, `priority`, `reporter`,
`found_in`, `score` и полный текст найденного фрагмента.

Человек, проект и статус — **отдельные аргументы, а не часть `query`**.
Фамилия, положенная в `query`, не найдёт ничего: исполнитель хранится полем, в
тексте задачи его нет.

## Типовые проблемы

**401 / 403 / 404 на `--check`.** В тексте ошибки написано, что проверять.
Коротко: 401 — токен не принят (Server/DC ждёт PAT в заголовке Bearer; в
сборках старше 8.14 токенов нет, нужны `JIRA_USER`/`JIRA_PASSWORD`); 403 —
токен принят, но прав не хватает либо сработал CAPTCHA-фильтр после неудачных
входов; 404 — неверный URL, у Jira часто есть префикс вида `https://host/jira`.

**В шапке `Окно: не задано`, хотя `JIRA_SINCE` прописан.** Контейнер поднят со
старым окружением:

```bash
docker compose up -d kb
```

```bash
docker compose exec kb printenv JIRA_SINCE
```

**Сузили окно, а задач в индексе столько же.** Так и должно быть: окно живёт в
выгрузке, а индексатор берёт всё, что лежит в каталоге, и чистит только те
задачи, которые переписывает. Нужна полная пересборка.

**Спросил про Jira — ответ пришёл из Confluence.** Модель позвала `kb_search`
вместо `jira_search`. Раньше это было вдвойне плохо: поиск по документации
искал по всей коллекции, включая задачи. Теперь `kb_search` источник `jira`
исключает, поэтому на вопрос про задачи он вернёт «ничего не нашлось» —
понятный сигнал вместо правдоподобной подмены. Если модель всё равно зовёт не
тот инструмент, добавьте в сообщение слово «jira» и проверьте, что правила из
`continue-config.example.yaml` доехали в ваш `~/.continue/config.yaml`.

**Инструмента не видно в Continue.** Проверьте по порядку: образ пересобран
(шаг 5 выше), VS Code перезапущен **полностью**, а не reload window — при нём
MCP-серверы не переподключаются, и включён режим **Agent**, а не Chat.

**Модель лезет в Jira без просьбы или не лезет по просьбе.** Гейт — слово
«jira» в сообщении — это инструкция модели, а не фильтр в коде. Жёстко
закрывается только политикой инструментов в самом Continue: «Ask first».

## Полная пересборка

Когда нужно выкинуть всё собранное и собрать заново — например, после сужения
окна. Порядок важен: чистим **до** новой выгрузки.

```bash
docker compose exec kb rm -rf /docs/jira
```

```bash
curl -X POST 'http://localhost:6333/collections/knowledge/points/delete?wait=true' -H 'Content-Type: application/json' -d '{"filter":{"must":[{"key":"source","match":{"value":"jira"}}]}}'
```

Удаляются только точки с `source=jira` — документы и код не затрагиваются.
Дальше обычная выгрузка и индексация.

Это же стоит делать раз в квартал: окно смотрит на `updated`, задачи, которые
давно не трогали, из выгрузки выпадают, но их точки в индексе остаются и сами
не удаляются.

## Чего нет

Удалённые и перенесённые задачи остаются в выгрузке и в индексе. Нет вложений,
истории изменений и связей между задачами. ACL не настоящие: в payload лежит
`acl_groups = ["jira:<PROJECT>"]`, но никто их пока не проверяет — на портах
аутентификации нет, и единственная реальная граница — то, что вы решили не
выгружать.
