# Граф кода

Тянет репозитории из git, строит граф через [Graphify](https://github.com/Graphify-Labs/graphify)
и отдаёт его в Continue по MCP на :8011.

```
git  ->  sync.sh  ->  Graphify (tree-sitter, офлайн)  ->  graph.json  ->  MCP
```

## Запуск

Указать репозитории в `.env` проекта:

```
CODE_REPOS=https://git.company.local/team/service-a.git,https://git.company.local/team/service-b.git
```

Приватные — с токеном прямо в URL:
`https://oauth2:ТОКЕН@git.company.local/team/service.git`

```powershell
docker compose up -d code-graph
```

При старте контейнер клонирует репозитории, строит граф и поднимает MCP.
Данные в `D:\code-data` (репозитории и граф), а не в образе — пересборка
не приводит к повторному клонированию.

## Обновление

```powershell
docker compose exec code-graph /app/sync.sh
```

Подтягивает изменения (`git fetch` + `reset --hard`), перестраивает граф,
сливает репозитории в общий. Разумно повесить на планировщик раз в час.

Клонирование поверхностное (`--depth 1`): нужен снимок кода, не история.

## Что можно спрашивать

Инструменты сервера: `query_graph`, `get_node`, `get_neighbors`,
`shortest_path`, `god_nodes`, `graph_stats`, `get_community`, плюс работа с
GitHub PR (в закрытом контуре бесполезна).

Вопросы, на которые он отвечает точно:

- кто вызывает эту функцию, что импортирует этот модуль
- что сломается, если изменить X (обратный обход)
- какие модули центральные — `god_nodes` находит то, от чего зависит всё
- как связаны две части системы — `shortest_path`

## Jenkins: пайплайны и шаги общей библиотеки

Graphify общую библиотеку Jenkins не видит: его настройки Groovy знают только
методы классов, а `vars/*.groovy` — скрипты с `call()` на верхнем уровне; к
тому же грамматика tree-sitter-groovy 0.1.2 (последняя) не разбирает
`def call(cfg)` и `Map args = [:]` — отсюда предупреждения
`first error at line 1, no symbols extracted`. И главное: связь «пайплайн ->
шаг» — соглашение Jenkins (шаг называется по имени файла), а не Groovy.

Поэтому `jenkins_graph.py` после сборки графа дописывает в него:

- **шаги** — `vars/abActions.groovy` -> узел `abActions`
- **пайплайны** — `Jenkinsfile*`, `*.jenkinsfile` -> узел `репозиторий/путь`
- **groovy-классы, зовущие шаги** через `steps.abActions(...)`
- **связи `calls`** между ними, в том числе между репозиториями

Спрашивать через `get_neighbors` с именем шага: `<--` — кто его вызывает,
`-->` — что вызывает он. `query_graph` идёт только вперёд и вызывающих не
покажет.

Вызовы находятся по именам известных шагов в коде без комментариев и строк
(`abActions(...)`, `abActions { }`, `abActions env: 'x'`,
`notifySlack "текст"`, `abActions.helper()`, `steps.abActions()`), а не
грамматикой — она как раз спотыкается. Не находится шаг, выбранный по имени из
переменной. Шаг с одним именем в двух библиотеках — связь `AMBIGUOUS`.

Graphify при этом не правится — его версия в образе не закреплена, правка
слетела бы при обновлении. Проверка: `docker compose exec code-graph python
/app/test_jenkins_graph.py`.

## Почему офлайн

`graphify update` разбирает код через tree-sitter локально: **ни сети, ни
ключей**. LLM нужен только для семантических меток по документам и картинкам,
нам это не требуется.

В образе `graphifyy[mcp]` — без extra `[mcp]` HTTP-транспорт не поднимется
(нужны mcp + starlette + uvicorn), а stdio для контейнера не годится.

## Ограничения

- **Аутентификации нет.** Сервер открыт всем, кто дотянется по сети. Внутри
  своей сети приемлемо; наружу выставлять нельзя. Ключ включается
  `--api-key` (или `GRAPHIFY_API_KEY`)
- **Python разбирается статически**, поэтому динамические вызовы
  (`getattr`, фабрики, декораторы) видны не всегда. Graphify помечает
  достоверность: `EXTRACTED` / `INFERRED` / `AMBIGUOUS`
- **Markdown тоже попадает в граф** — в `query_graph` лезут заголовки
  документации. Для структурных вопросов используйте `get_neighbors`
  и `shortest_path`, они точнее
- Смысловой поиск по коду («где реализована авторизация») этот сервер не
  делает — для него нужна отдельная коллекция в Qdrant, пока не сделано
